# Token 成本与上下文增长：机制、数字与对策

> 记录时间：2026-10-09 ｜ 数据来源：本机 `~/.dsh` 真实会话统计 + DSH 源码默认参数

---

## 一、先纠正一个直觉：会长大的不是文件，是会话

| 东西 | 增长速度 | 说明 |
| --- | --- | --- |
| 工作区文件（daily / tracking） | **每天 +15~20KB** | 一年约 6MB。**不进入上下文**，只在你读取时才占用 |
| 会话上下文 | **每天 +20~35k tokens** | 这才是真正复利增长的部分 |

关键区别：**文件是磁盘上的数据，不会自己变成 token。** 只有"被读取"的那部分才进上下文。

所以每次运行的真实上下文 = **固定启动开销（读文件） + 会话历史（以前所有运行）**。

- 固定启动开销：约 **30k tokens**（含系统提示、README、playbook、模板、趋势追踪、当天日报）—— **线性、可控**
- 会话历史：**每天累加**，这是唯一复利的部分

**所以最省 token 的做法不是少写文件，而是别让历史堆积在同一个会话里。**

---

## 二、你的问题 1：持续复利增加吗？

**会话内是累加的，但每次运行要付的是"当时整个上下文"，不是"新增部分"。**

每次运行真实计费输入 ≈ `固定开销 + 该会话全部历史`。

以本机实测为参照（一天跑一次）：

| 天数 | 该次运行的上下文规模 | 说明 |
| --- | --- | --- |
| 第 1 天 | ~30k | 只有文件启动开销 |
| 第 3 天 | ~80k | 历史开始占主导 |
| 第 7 天 | ~170k | 历史约为启动开销的 5 倍 |
| 第 14 天 | ~350k | 接近需要干预 |
| 第 20~25 天 | ~800k | **触发压缩** |

**实测对照**：本机那个自动化会话，跑完 1 次自动化 + 6 轮对话后是 **120k（12%）**。

## 三、你的问题 2：会压缩吗？会失真吗？

**会压缩，参数我查到了**（`dsh-compaction-basic` 默认值）：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `thresholdRatio` | **0.8** | 上下文压力达到 1M 的 **80%（约 800k）** 时触发压缩 |
| `retainRatio` | **0.16** | 压缩后只保留约 **16%** 的逐字内容，其余由 LLM 摘要替代 |

也就是说，**在 800k 那一刻，历史的一部分会被摘要替换掉 —— 这不是无损的。**

DSH 还有其他辅助机制降低压力：`compaction-tool-result-pruner`（精简工具返回）、`compaction-image-offload`（图片占位化）。

### 但这里有两个好消息

**好消息 1：压缩不会破坏正确性。**
这个系统的设计恰好是"**真相在文件里，不在对话里**"。压缩丢失的只是"我上次怎么说的"这类对话记忆；而：

- 答案的**完整内容**在 `tracking\趋势追踪.md` 的「完整答案存档」
- 每天的依据、验证方式、要盯的信号，都在 `daily\` 里
- 新会话开局读这几个文件，**几秒就能恢复到可用状态**

**好消息 2：你其实不该等它压缩。** 压缩触发时上下文已经 800k，那次调用本身就很贵（还多一次摘要输出）；而且在压缩之前，你已经在为堆积的历史持续付费了。

正确做法是**主动轮换，不等它压缩**。

## 四、你的问题 3：持续费钱吗？费多少？

### 成本结构（用你自己会话里的真实数字）

| 指标 | 含义 | 本机自动化会话实测 |
| --- | --- | --- |
| `cacheReadTokens` | 命中提示缓存的输入 | 数千万级（**便宜档**） |
| `uncachedInputTokens` | 未命中缓存的输入 | 数万~数十万级（**全价档**） |
| `outputTokens` | 生成 | 数十万级 |

**关键：绝大部分输入是 cache read，不是全价输入。** 所以"总 token 数字很大"不等于"很贵"。

但有两个真实的费钱点和风险点：

1. **缓存未命中 = 全价重算。** 每次定时运行如果间隔太久（缓存过期），整个上下文前缀会按未命中输入计费。**上下文越大，这一下越贵。** 这是最大的成本尖峰。
2. **上下文越大，每次运行越贵。** 因为每次都要把整个历史过一遍 —— 即使大部分走缓存，也在累积成本。

### 结论

- **不是"无限复利爆炸"**，而是"**每天贵一点，且到了一个点会突然变贵**"。
- 真实风险不在钱，在**质量**：接近压缩线时，压缩闸口可能在你需要它记住某个 30 天前判断的时候触发。

## 五、对策（按性价比排序）

| 优先级 | 做法 | 效果 | 成本 |
| --- | --- | --- | --- |
| ★★★ | **每 2~4 周轮换会话**（新建会话 + 重建定时任务） | 上下文归零，新会话读文件几秒恢复 | 几分钟人工 |
| ★★★ | **压缩线前主动轮换**：占比超 **30%** 或出现第一次压缩时立刻换 | 避免"最贵且最失真"的时刻 | 同上 |
| ★★☆ | **每次运行用 `session-health.mjs` 看一眼** | 量化监控，不靠感觉 | 一条命令 |
| ★★☆ | **按节读取，不整份读** | 趋势追踪文件逐日变长，只读「答案登记表」+「日志最近 30 天」 | 改一行提示词 |
| ★★☆ | **保持一次性命令输出简短** | 抓取脚本已经只输出条目单，不要 dump 原始 HTML | 已做到 |
| ★☆☆ | 长回答不要反复重读旧日报 | 旧日报是按日期归档的，只在需要引用时读 | 习惯 |

### 为什么"轮换会话"是最优解

因为**会话是可丢弃的执行环境，文件才是状态**。这套系统的状态 100% 在磁盘上：

- 换会话 → 读 `README.md`、`analysis-playbook.md`、`tracking\趋势追踪.md` → 立刻继续，**不丢任何东西**
- 唯一要重做的事：把定时任务在新会话里重建一次（提示词已经导出成 `video\任务提示词.md`）

## 六、监控命令

```powershell
cd D:\自动化任务
node scripts\session-health.mjs
```

输出每个会话的上下文占用、距离压缩线还有多少、以及缓存读入/未缓存输入/输出的比例。
**判断会话是否"贵"，看缓存读入与未缓存输入的比例，而不是看总 token 数。**

**观察指标**：自动化会话的"上下文占比"超过 **30%** → 该轮换了。

---

## 七、一句话总结

> **文件不会复利，会话才会。** 上下文到 800k 会触发一次有损压缩，压缩前你已经在为堆积的历史付费。
> 所以别想着"压缩会不会失真"，而是**赶在压缩之前把会话换掉** —— 因为真相在文件里，换会话零损失。
